# Phase-2 Dataset Governance

This document defines governance rules for all baseline datasets and pinned golden bundles used by Phase-2.

## Scope

Governed assets include:

- `Phase-2/datasets/manifest.json`
- `Phase-2/datasets/traces/*.csv`
- `Phase-2/datasets/residency/*.csv`
- `Phase-2/golden_out_*/` bundles that are used as replay references
- Any manifest generated by pipeline scripts (for example `spike_manifest.json`, `qemu_manifest.json`, `gem5_manifest.json`)

## Ownership And Review

- Dataset changes require at least one Phase-2 maintainer review.
- Any change that modifies trace semantics or residency masks requires replay evidence in the same PR.
- Any change to a pinned golden bundle requires updated provenance metadata (see below).

## Versioning Rules

- `dataset_version` is mandatory in each manifest.
- `dataset_version` must be bumped whenever any governed input changes:
  - trace list/order/content
  - residency masks
  - default window (`window_us_default`)
  - adapter thresholds encoded into a generated dataset
- Version format should be stable and target-aware, for example:
  - `phase2-v2`
  - `gem5-golden-v1-60traces`
  - `qemu-golden-v1-40traces`

## Required Provenance Metadata

Pinned bundles must include:

- Manifest file with `dataset_version`, `traces`, and `residency_masks`
- `trace_index.csv` with workload/size/flag metadata
- Adapter metadata in each run (`adapter_meta.json`) and/or normalized hashes in summary artifacts
- Run-level outputs:
  - `*_windows.csv`
  - `*_summary.json`
  - `plots/invariant_report.csv`

Recommended:

- `summary.json` with pass/fail counts
- `plots/common_summary_*.csv`

## Factor Labeling For Flag Metadata

When documenting or summarizing `flag_mode` variants (`none`, `branch_mispredict`, `cache_pressure`, `both`), use:

- Workload/orchestration factors
- Runtime/OS factors
- Microarchitectural timing factors
- Measurement overhead

Interpretation rule:

- On Spike/QEMU, `branch_mispredict` and `cache_pressure` are synthetic workload/orchestration factors (not microarchitectural timing models).
- On gem5/hardware contexts, those same perturbations may also surface microarchitectural timing factors when timing is modeled.

Methodological note: Spike and QEMU do not model microarchitectural timing; gem5 and hardware platforms may.

## Immutability Rules

- Pinned dataset folders are immutable after merge.
- If a pinned bundle must change, create a new versioned output folder and manifest version.
- Do not overwrite historical golden folders in-place.

## Validation Gates For Dataset Changes

Minimum required checks before merge:

```bash
cd Phase-2
python3 tests/check_adapter_fixtures.py
python3 tests/check_determinism.py --targets qemu --workload hello --workload-size test --allow-nonzero-exit
python3 run_cross_target_suite.py --targets cpu qemu --workloads hello --workload-size test --allow-nonzero-exit
python3 tests/run_golden_suite.py --manifest datasets/manifest.json --outdir /tmp/phase2_dataset_replay
```

For gem5 bundle updates, also run:

```bash
cd Phase-2
python3 tests/run_gem5_golden_pipeline.py \
  --workloads fm_loopback fm_mm fm_read fm_write matmul \
  --workload-sizes test tiny small med large \
  --emulated-flags none branch_mispredict cache_pressure both \
  --time-us 256 --window-us 256 \
  --gem5-bin /abs/path/to/gem5.opt \
  --gem5-root /abs/path/to/gem5 \
  --gem5-config /abs/path/to/gem5/configs/deprecated/example/se.py \
  --outdir golden_out_gem5_matrix_<version>
```

## PR Checklist For Governed Changes

- [ ] `dataset_version` bumped in affected manifest(s)
- [ ] provenance artifacts (`trace_index.csv`, manifest, invariant report) included
- [ ] determinism and cross-target smoke checks passed
- [ ] no in-place mutation of existing pinned bundle directories
